# Design: Content Knowledge Graph

Status: Draft v0.2
Owner: Scott
Last updated: 2026-10-15

Changes in v0.2: corpus, scope, hardware, and evaluation decided (section 2); include resolution and docs-specific Markdown handling added to ingest (5.1); tier 3 gating and CPU defaults (5.2); gold set made optional (5.6); domain condition types added (6); open questions resolved (12).

## 1. Purpose

Build a pipeline that reads a large set of content and produces a knowledge graph of the information the content contains: the things it describes and how they relate. The graph models the subject matter (the domain), not the structure of the documents. Document structure is kept only as provenance, so every fact can point back to the text that supports it.

This version is a conceptual exercise: the goal is to see the results of the process end to end, not to reach production quality.

## 3. Goals

1. Extract entities and relationships that conform to a single, versioned schema.
2. Attach provenance to every fact: source document, chunk, character offsets, evidence text, extraction method, and model version.
3. Represent conditional facts (for example, "applies only to version 3") without losing the condition.
4. Resolve different names for the same entity to one canonical ID.
5. Produce repeatable results: the same input and configuration give the same graph.
6. Reprocess only content that changed.
7. Use open-source software throughout. Ask before adding any dependency that is not open source.

## 4. Non-goals for this version

- A user interface or graph visualization
- Question answering, chat, or GraphRAG community summaries
- Writing changes back to the source content
- Multi-user or server deployment
- Formal precision and recall measurement against a hand-annotated gold set

## 5. Architecture

The pipeline runs as a sequence of stages. Each stage reads the previous stage's output from disk and writes its own, so any stage can be rerun alone.

```
content files
  -> [1 ingest]   chunks.jsonl
  -> [2 extract]  mentions.jsonl, assertions.jsonl
  -> [3 resolve]  entities.jsonl, assertions.resolved.jsonl
  -> [4 load]     Oxigraph store (RDF)
  -> [5 validate] SHACL report
  -> [6 evaluate] competency question results, spot-check sample, reports
```

### 5.1 Ingest

- Load files through a loader interface, one loader per format. The corpus is Markdown only, so start with a Markdown loader. Docling is not needed for this corpus.
- Select files with include and exclude globs from `config.yaml`. The first run uses an explicit include list (the slice).
- **Front matter.** Parse the YAML front matter and store it as document metadata (`title`, `description`, `ms.topic`, `ms.subservice`, `ms.date`). Normalize whitespace and trailing comments in values. Front matter is provenance, not extracted facts.
- **Includes.** Resolve `[!INCLUDE [...](path)]` before chunking, recursively, with cycle detection.
  - Paths relative to the article, and `~/articles/...` paths inside the repo, are resolved inline.
  - Paths into repositories that are mapped in only at publish time (`~/reusable-content/...`, `~/azure-policy-autogen-docs/...`) are replaced by a placeholder marker of known form, such as `[[UNRESOLVED_INCLUDE: <path>]]`. Each one is logged to `review/unresolved_includes.csv` with article, line, and target path. Placeholders are excluded from extraction.
  - Keep a source map from resolved-text offsets back to the original file and offsets, so provenance can name both the article and the include file a span came from.
- **Docs-specific Markdown.**
  - Tabbed sections (`# [Python SDK](#tab/python)` ... `---`) are not headings. Each tab becomes its own chunk section, and the tab label is recorded as an `interface` hint on the chunk.
  - Lines starting with `#` inside fenced code blocks are not headings.
  - Callouts (`> [!NOTE]`, `> [!IMPORTANT]`) are kept as text; the callout type is recorded on the chunk.
  - Preview banners (preview include files) set a `release_status: preview` hint on every chunk of the article.
  - Links into `v1/` and to other services are recorded as references but not followed.
- Split each document into chunks at heading boundaries, with a target of about 600 tokens and a hard maximum of 1,200. Smaller chunks improve recall in LLM extraction (Edge et al., 2024). **Never split a Markdown table**; a table larger than the maximum is split by rows, repeating the header row in each part.
- Give every chunk a stable ID: `<relative file path>#<heading slug>[-<n>]`. IDs must not change when unrelated files change.
- Store a SHA-256 hash of each chunk's resolved text. Later stages skip chunks whose hash has not changed. A change to an include file changes the hash of every chunk that uses it.
- **Normalized text.** All offsets refer to normalized text: UTF-8 without BOM, line endings converted to LF. This keeps offsets and hashes identical whatever git's `core.autocrlf` did to the working copy.
- **Merging and splitting.** Consecutive sections with the same interface merge while the chunk stays within the target. A heading with no text of its own (an H2 directly above an H3 or a tab group) always joins the next chunk. Later parts of a split section repeat the section's heading line.
- **Outputs.** `documents.jsonl` holds one record per article: path, title, selected front matter, resolved-text hash, includes used, and chunk IDs. `chunks.jsonl` holds one record per chunk: ID, heading path, text, hash, size estimate, hints (interface, release status, callouts, has_table, has_code), and `pieces`. Pieces tile the chunk text; each maps a range of it to a source file and offset, or marks a placeholder. Chunk text can be non-contiguous in the source (repeated headings and table headers), and pieces still map every character back.

### 5.2 Extract (three tiers)

Run the tiers in order on each chunk. Each tier records which method produced each result.

| Tier | Method | Output |
|---|---|---|
| 1 | spaCy `PhraseMatcher` built from the vocabulary file (preferred and alternate labels) | Entity mentions with exact offsets and vocabulary IDs |
| 2 | GLiNER zero-shot NER, using entity class names from the schema as labels | Additional entity mentions with scores |
| 3 | Local LLM through Ollama, with JSON-schema structured output generated from the LinkML schema | Relationships (assertions) among mentions |

Tier 1 and 2 rules:

- **Masking.** Neither tier matches inside fenced code, link targets and bare URLs, Learn directives (`:::image ...:::`), HTML comments, callout markers (`[!NOTE]`), or unresolved-include placeholders. Each kind can be turned off in `config.yaml`. Matches inside masked text are logged as dropped, with the mask kind as the reason.
- **Tier 1 case rule.** Single-word labels with a capital letter (Reader, Owner, Bicep) match only with that exact case, so the word "reader" doesn't become the Reader role. Every other label matches case-insensitively, along with its regular plural (endpoint → endpoints, policy → policies). Where matches overlap, the longest wins. spaCy runs with a blank English tokenizer, so no spaCy model is downloaded.
- **Tier 2 labels and windows.** GLiNER's labels are the schema's concrete domain classes written as words ("ComputeTarget" becomes "compute target"), with overrides in config. Chunk text is cut into windows of at most `max_words` GLiNER tokens, avoiding masked text and breaking at line ends, and offsets are mapped back to the chunk. A prediction whose text doesn't match the chunk at its offsets is dropped.
- **Merging.** Tier 1 wins wherever a tier 2 span overlaps it, because tier 1 carries an exact vocabulary ID. The overlapping tier 2 mention is logged as dropped.
- **Outputs.** `mentions.tier1.jsonl` and `mentions.tier2.jsonl` (each tier's kept mentions), `mentions.jsonl` (merged), and `mentions.dropped.jsonl` (every rejected mention with its reason). Each mention conforms to the generated `Mention` model; `Mention.vocab_id` holds tier 1's vocabulary match.
- **Changed-only.** `--changed-only` reuses a chunk's previous mentions when its hash and the tier's settings (vocabulary file, masks, model, labels, threshold) are unchanged, tracked in the SQLite state database. The result is identical to a full run.

Tier 3 rules:

- Pass the chunk text plus the mentions found by tiers 1 and 2. Ask the model only for relationships among them, plus any entities it finds that the earlier tiers missed.
- Every assertion must include an `evidence` field containing text copied from the chunk. Reject any assertion whose evidence is not an exact substring of the chunk.
- Use temperature 0. Record the model name and version on every assertion.
- Make the model configurable in `config.yaml`. Default: `qwen2.5:7b-instruct` (Apache 2.0, Q4_K_M, Ollama digest `845dbda0ea48`), chosen for reliable structured JSON output and no reasoning phase.
- **Gating.** Run tier 3 only on chunks with at least two distinct mentions from tiers 1 and 2. The threshold is a config setting. Skipped chunks are logged with the reason.
- **CPU runtime (measured in Phase 4).** On an Intel i5-12400F with 16 GB RAM, a 10-chunk benchmark took a median of 30 seconds and a mean of 25 seconds per chunk (about 2,600 prompt and 860 output tokens per chunk). Ollama caches the shared system prompt between calls. Of the slice's 1,040 chunks, 953 pass the gate, so a full slice run takes about 6.5–8 hours.
- **Prompt and output schema.** Both come from `schema/generated/ckg.predicates.json` (classes, predicates with domain and range, condition types), written by `tools/gen_schema.py`. The instruction text lives in `prompts/tier3_system.md`. The output schema limits predicates, classes, and condition types to schema values, and caps assertions per chunk (`max_assertions_per_chunk`) so long lists don't hit the output token limit.
- **Checks on each assertion.** Known predicate; evidence found in the chunk (exactly, or differing only in whitespace, in which case the chunk's exact text is stored); subject, and for relations the object, found in the chunk; no self-references; enum values valid; no duplicates. A subject or object that tiers 1 and 2 missed becomes a new `llm` mention, written to `mentions.tier3.jsonl` and merged into `mentions.jsonl`. If a response was cut off, its complete items are still checked and the cut is logged. Assertions refer to mention IDs until resolution replaces them with entity IDs.
- **Resumable runs.** Each response is stored in SQLite as soon as it arrives, keyed by chunk hash and a settings hash (model digest, system prompt, output schema, tier 3 settings, and a prompt-construction version). Reruns reuse stored responses. `ckg extract --tier 3 --limit N` runs N gated chunks spread evenly through the slice, for benchmarks. Record progress per chunk in SQLite so an interrupted run resumes where it stopped.
- Chunk hints from ingest (tab interface, preview status) are passed to the model as candidate conditions.

The schema-driven approach follows the SPIRES method used in OntoGPT (Caufield et al., 2024). Consider using OntoGPT directly for tier 3 if it fits; otherwise implement the same pattern.

### 5.3 Resolve

1. Normalize names (case, whitespace, punctuation).
2. Match against vocabulary labels. A match assigns the vocabulary's ID.
3. For unmatched names of the same class, compare with `rapidfuzz` string similarity and embedding similarity. Merge above a high threshold, queue for review between thresholds, and keep separate below a low threshold. Thresholds go in `config.yaml`.
4. Write unresolved and borderline cases to `review/resolution_queue.csv` for a person to decide.
5. Keep every original surface form as an alias on the canonical entity.

### 5.4 Load

- Store the graph in Oxigraph (embedded, through `pyoxigraph`). No server is needed, and it supports SPARQL.
- Load each assertion two ways: as an `Assertion` node that carries conditions and provenance, and as a direct triple (subject, predicate, object) for simple queries.
- Loading a changed chunk first deletes everything previously derived from that chunk.

### 5.5 Validate

- Generate SHACL shapes from the LinkML schema and run them with `pySHACL`.
- Report violations by type. Domain and range violations (for example, a relationship whose subject is the wrong class) must be listed individually.

### 5.6 Evaluate

There is no gold set for this version. Evaluation uses checks that need no annotation:

- **Competency questions.** Store each competency question with a SPARQL query in `eval/competency_questions/`. Report which queries return results, and include the results, so a person can judge whether they answer the question.
- **Spot check.** Write a random sample of about 50 assertions (fixed seed) with their evidence text and conditions to `review/spot_check.csv`, for a quick manual read to estimate precision.
- **Structural reports.** SHACL violations, rejected assertions with reasons, gated-out chunks, and unresolved includes.
- **Unmapped mentions.** Log mentions that did not map to any schema class to `review/unmapped_mentions.csv`, with counts. Frequent unmapped mentions suggest missing classes.
- **Optional gold set.** The comparison code (precision, recall, and F1 per entity class and relationship type against `eval/gold/`) may be built, but no phase waits on it.

## 6. Schema

The schema is written in LinkML and is the single source of truth (Moxon et al., 2021). Generate Pydantic models, JSON Schema, SHACL, and OWL from it with the LinkML generators. Do not hand-edit generated files.

Split it into two files:

- `schema/core.yaml`: classes that do not depend on the domain. Claude Code owns this file.
- `schema/domain.yaml`: domain classes and relationships. Scott owns this file. Claude Code drafted it from the competency questions; Scott approved v0.2 (34 classes, 35 relationship slots) on 2026-10-15.

Generate with `uv run python tools/gen_schema.py` (`--check` fails if any output is stale; a test runs the same check). Outputs: Pydantic models in `src/ckg/generated/model.py` (importable by the pipeline, and depending only on Pydantic), and JSON Schema, SHACL, and OWL in `schema/generated/`. SHACL shapes are open (not closed), so nodes may carry triples beyond the schema; domain and range checks still apply. LinkML is a development dependency only.

Core classes:

| Class | Purpose | Key slots |
|---|---|---|
| `Entity` | Base class for all domain entities | `id`, `entity_type`, `label`, `aliases`, `vocab_id` |
| `Assertion` | One extracted fact | `subject`, `predicate`, `object` or `object_value`, `negated`, `conditions`, `confidence`, `provenance` (one or more) |
| `Condition` | A qualifier on an assertion | `type`, `value` |
| `Provenance` | Where a fact came from | `source_doc`, `include_file`, `chunk_id`, `start`, `end`, `evidence`, `method`, `model`, `extracted_at` |
| `Mention` | A span of text that refers to an entity | `chunk_id`, `start`, `end`, `text`, `predicted_class`, `entity`, `method`, `score`, `model` |
| `KnowledgeGraph` | Container for serializing entities, mentions, and assertions | `entities`, `mentions`, `assertions` |

- `entity_type` names the entity's class, so serialized entities keep their type.
- `object_value` holds a literal object for attribute predicates (for example, a `Limit`'s value). An assertion has exactly one of `object` and `object_value`; extraction code enforces this, since the generators don't.
- `negated` records facts stated in the negative ("doesn't support"), which are common in this content.

`Condition.type` has the range `ConditionType`, which the domain schema defines. It must include every value of core's `CoreConditionType` (version, role, environment, time, other); a test checks this. This domain adds `region`, `release_status`, `interface`, `endpoint_type`, `model_flavor`, `network_mode`, `workspace_configuration`, and `task_type`.

`Provenance.include_file` is set when the evidence span came from a resolved include file.

Domain classes subclass `DomainEntity`, an abstract subclass of `Entity`. Domain relationships are slots with an explicit `domain` and `range`, and each is attached to its domain class: relationships whose subject can be any domain entity sit on `DomainEntity`, and the rest on their specific class. Attaching them is what makes them appear in the SHACL shapes. Class names in `domain.yaml` match the `ckg:domainClass` values on the vocabulary's concept schemes.

## 9. Command-line interface

```
ckg ingest   --input <dir>
ckg extract  [--tier 1|2|3] [--changed-only] [--limit N]
ckg resolve
ckg load
ckg validate
ckg evaluate
ckg run      # all stages, changed content only
```

All settings come from `config.yaml`. No setting may be hardcoded.

## 10. Build phases

Work one phase at a time. At the end of each phase, stop, summarize what was built, and wait for review before starting the next.

| Phase | Scope | Done when |
|---|---|---|
| 0 | Repo scaffold, `pyproject.toml`, config loading, CLI skeleton, 10 sample files taken from the slice | `ckg --help` runs; tests pass in CI-equivalent local run |
| 1 | Ingest: front matter, include resolution with placeholders, docs-specific Markdown handling, chunking with stable IDs and hashes | Rerunning on unchanged input produces identical `chunks.jsonl`; editing one file changes only that file's chunks; editing an include changes the chunks of every article that uses it; no table is split mid-row |
| 2 | Core LinkML schema, approved domain schema, code generation | Generated Pydantic, JSON Schema, and SHACL build without errors |
| 3 | Extraction tiers 1 and 2 | Mentions have correct offsets; a test confirms `text == chunk[start:end]` |
| 4 | Extraction tier 3, with gating and resumable runs | Every stored assertion's evidence is an exact substring of its chunk; rejected assertions are logged; CPU time per chunk is measured on the slice |
| 5 | Entity resolution and review queue | Vocabulary aliases resolve to one ID; borderline pairs appear in the queue |
| 6 | Load into Oxigraph and SHACL validation | A SPARQL query returns assertions with conditions and provenance; reloading a changed chunk leaves no orphaned triples |
| 7 | Evaluation: competency question queries, spot-check sample, reports | Competency question results, spot-check CSV, and reports are generated from the command line |

## 11. Engineering rules

- Write tests for each phase. Cover offsets, stable IDs, idempotent reruns, include resolution, and evidence checks.
- Results must be deterministic for a fixed configuration and model version.
- Log every rejected, skipped, or unmapped item with a reason. Do not drop data silently.
- Keep domain-specific terms out of code. They belong in the schema, the vocabulary, or the config.
- Ask before adding a dependency, changing the schema in `domain.yaml`, or changing a decision in this document.
